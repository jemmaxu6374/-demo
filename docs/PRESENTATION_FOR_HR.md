# 实时精准个性化赋能模型：设计准备与 Demo 讲解

> 面向人力资源管理专业研究生与导师的展示文稿
> 时长建议：40 分钟讲解 + 20 分钟互动
> 对应 Demo：https://jemmaxu6374--demo.streamlit.app（或本地 `streamlit run app/streamlit_app.py`）

---

## 开场：我们到底在解什么问题？

各位老师、同学好。今天想和大家分享一个做了一段时间的小项目——**面向知识工作者的实时精准个性化赋能模型**，以及它背后的设计准备。

在进入技术细节之前，我先把这件事情放回到人力资源管理的大背景里。过去二十年，企业在"员工发展（Employee Development）"上的投入其实一直在增长，但传统培训体系有三个几乎没法回避的问题：

**第一，时机错位**。培训往往是"集中发布、批量消费"——新员工入职集中培训、年度学习计划统一下发、KPI 周期结束后再做复盘。但人真正产生学习需求的时刻，是他在处理某个具体任务、卡在某个具体问题上的那一刻。等到两周后再去上那门预先排好的课，学习动机和场景早就漂移了。

**第二，颗粒度过粗**。绝大多数 LMS（Learning Management System）只能按岗位、职级、部门推送课程，看不见"这个人此时此刻在做什么任务、缺哪一项具体能力"。于是我们看到的是"全体产品经理必修用户研究课"这类粗线条的指派，落到个体上命中率非常低。

**第三，形态单一**。一提到"赋能"，很多人脑子里第一反应就是"上课"。但学习科学早就告诉我们，70-20-10 法则——**70% 的能力成长来自在岗实践、20% 来自向他人学习、只有 10% 来自正式培训**。把所有预算砸在那 10% 上面，天然就是投入错位。

所以我们要做的事情可以一句话概括：

> **把"员工此刻所做的事"、"他已经具备的能力"、"他正要补的缺口"、"组织里可以调用的全部学习资源"这四件事打通，做到"他需要什么，系统恰好在那一刻把最合适的那一小份东西推到他面前"**。

这里有四个关键词值得展开：**实时**（跟着行为流走，不是跟着培训周期走）、**精准**（到具体能力节点，不是到岗位或部门）、**个性化**（每个人看到的推荐不同，甚至同一个人今天和下周看到的也不同）、**赋能**（不只是"培训"，还包括实战项目、导师、案例、工具、Prompt 等七种形态）。

接下来我会从**设计准备**和**Demo 讲解**两条线展开。

## 第一部分：做这样一个模型，你需要准备哪些东西？

很多 HR 同学听到"AI 赋能"会觉得是黑箱，其实越深入越会发现——**数据和设计本身的工作量，远大于模型调用本身**。我把准备工作分成五层。

### 1. 能力本体（Competency Ontology）：一切的起点

这是整个系统的"元数据基座"。如果没有一套结构化、可计算的能力体系，后面一切推荐、Gap 分析、画像更新都无从谈起。

我们在 Demo 里设计了 **4 大类 × 36 个能力节点** 的本体：

| 大类 | 示例节点 | 衰减特性 |
|---|---|---|
| 硬技能（hard） | 编程-Python、编程-TypeScript、数据库-SQL、分布式-Kafka、机器学习-特征工程 | 一年衰减到 37% |
| 软技能（soft） | 沟通表达、问题拆解、跨团队协作、反馈给予、优先级判断 | 三年衰减（metaskill 稳定） |
| 领域知识（domain） | 推荐系统、广告风控、IM 协议、支付合规 | 两年衰减 |
| 工具熟练度（tool） | GitHub Copilot、Figma、Prometheus、Notion | 一年衰减 |

**设计取舍**：有人会问，为什么不直接用 O\*NET（美国劳工部能力词典，数千个 skill 节点）？——因为颗粒度必须匹配数据量。Demo 样本只有 20 名员工、10 份 JD，节点太细会让每一项的样本覆盖率趋近于零，模型学不到东西。真实企业部署时，建议从 200–500 节点起步，按岗位包分批扩展。

**给 HR 的启示**：这一步其实是"胜任力建模"的数字化落地。HR 同学熟悉的能力词典（Spencer、Mercer、Hay、华为BLM 等）都可以作为本体的语义源——区别只在于，过去这些词典停留在 Word 表格里，现在要变成**机器可读、可度量、可追溯**的 JSON 结构。

### 2. 员工与岗位画像数据

**员工侧**需要两类数据：

- **静态基线**：简历、项目经历、自评问卷、上一轮绩效评估。这部分结构化后叫 `base_competencies`，是每位员工能力分布的起点。
- **动态行为流**：过去 6 个月里员工产生的所有数字化痕迹。

**岗位侧**（JD Profile）需要：

- JD 自由文本（传统招聘用）
- 结构化能力清单：每个能力节点的 `need_level`（期望等级）+ `weight`（权重）

**一个关键设计决策**：`base_competencies` 不完全由 LLM 从简历抽取，而是**人工预置 + LLM 增量补充**。原因是简历和项目经历措辞多样，LLM 抽取一致性有上限；人工预置可以保证画像的"正确"底线，LLM 负责发现人工遗漏的细节。这也对应了生产环境的常见做法：**上一轮模型的产出 + 本轮人工校正 = 新一轮的 base**，形成数据飞轮。

### 3. 行为事件流：系统的"神经末梢"

这是整个实时系统最关键、也最容易被低估的一块。我们设计了 **6 类数字化行为事件**：

| 事件类型 | 数据源 | 颗粒度 |
|---|---|---|
| `task_event` | 项目管理系统（TAPD / Jira）的任务状态流转 | 单条任务 |
| `code_event` | Git commit / PR / Code Review | 单次提交 |
| `doc_event` | 文档系统（Confluence / 飞书 / 语雀）的产出与评论 | 单篇文档 |
| `learning_event` | LMS 学完课程 / 阅读文档 / 完成微课 | 单次学习 |
| `meeting_event` | 会议系统的参会与发言记录（如有） | 单次会议 |
| `feedback_event` | 360 反馈 / 1:1 纪要 / OKR 对齐记录 | 单次反馈 |

Demo 里我们为 20 名员工 × 6 个月生成了 **9400 条事件**，平均每人每月 78 条。这个量级符合真实知识工作者的行为密度。

**为什么行为流比自评和考试更重要？** 因为它有两个不可替代的优势：一是**自动、高频、被动采集**，不增加员工负担；二是**行为即证据**，比自我报告更抗博弈（员工可能在问卷里高估自己，但不会故意把 Code Review 打回率刷高）。

**行为流的伦理底线（必须提前准备）**：知情同意、数据脱敏、可随时关闭/导出/删除、权限审计可追溯、本人永远可见自己的画像。这些不是"上线后再补"，而是系统架构里一开始就要写进去的护栏——否则上线那一天就是合规事故那一天。

### 4. 赋能资源池：七类学习形态

传统 LMS 只管课程，这是最大的盲区。我们的资源池按 70-20-10 法则设计成**七类 + 一类工具正交**：

| 分组 | 占比 | 具体形态 | Demo 中的字段 |
|---|---|---|---|
| 🎯 在实践中学 | 70% | 内部项目 / Hackathon | `internal_projects.json` |
| | | 沙盒 Lab 环境 | `labs.json` |
| 👥 向他人学 | 20% | 导师 1:1（静态导师池 + 动态 Expert Finder） | `mentors.json` |
| | | 过往案例库（别人做过并复盘的问题） | `case_studies.json` |
| | | Tech Talk / 学习社群 | `tech_talks.csv` + `communities.json` |
| 📚 系统学习 | 10% | 课程（含微课） | `courses.csv` |
| | | 技术文档 / 书籍 / 论文 | `readings.csv` |
| 🛠️ 工具直接用 | 正交 | AI Copilot / 工具 | `tools.csv` |
| | | Prompt 模板库 / 工作流 SOP | `prompt_library.json` |

**"工具"为什么是正交的？** 因为它本质上不是"学"，而是"让你不需要学也能产出"。把 Copilot 和 Python 课程放在一个排名里，逻辑上就错了——前者是 ROI 问题（立刻能用），后者是投入产出周期问题（几周后才见效）。

**实测数据**：Demo 资源池共 155 条。这是"够讲清楚机制"的最小量级。真实企业应该把这里扩到 5000–10000 条，并且**持续运营**——因为资源本身会陈旧（一年前的 LLM 教程今天多半不能看了）。

### 5. Skill 体系：AI 到底在做什么

这是我最想跟 HR 同学强调的一点——**AI 在这个系统里不是一个"大脑"，而是被拆成了若干个专业 Skill（技能）**。每个 Skill 只做一件事，有清晰的输入输出和验证规则。我们的六个核心 Skill：

| Skill 名 | 职责 | 输入 | 输出 |
|---|---|---|---|
| **ExtractEmployee** | 从简历 / 项目描述中抽取能力标签 | 自由文本 | `CompetencyTag[]` 含 level、confidence、evidence |
| **ExtractJob** | 补齐 JD 里未显式列出的能力需求 | JD 文本 | 能力需求增量 |
| **RankGap** | 对 Gap 列表做优先级裁判 | gap 结构化差值 | 带 rationale 的优先级 |
| **RerankResource** | 对召回的资源做二次精排（含 `learning_mode` 约束） | Top-20 候选 | Top-5 + 推荐理由 |
| **GeneratePathway** | 合成 30 / 60 / 90 天成长路径（带 mode 组合约束） | Gap + 资源 | 三阶段路径（每阶段含 experiential/social/formal 至少各 1） |
| **AttributeEvent** | 把单条行为事件归因到若干能力节点的 Δlevel | 事件文本 | 能力 delta 列表 |

**为什么这样拆？** 有三个好处：

1. **可验证**：每个 Skill 的输出都走 Pydantic schema 校验，LLM 幻觉会在 schema 层被挡住
2. **可替换**：某个 Skill 想从 OpenAI 换成本地模型，不影响其他部分
3. **可降级**：每个 Skill 都提供 Mock 实现，连不上真实 LLM 时整个系统照样能跑通（这也是为什么我们的在线 Demo 不需要 API Key）

### 6. 模型框架：静态 + 动态 + 交互三层演进

这是我们把整个系统组织起来的三阶段架构。

**Phase 1 静态基线**：简历 + JD → Gap → 七路推荐 → 30/60/90 天路径。目标是把"一次性的职业规划咨询"变成可在 3 秒内生成的在线服务。

**Phase 2 动态画像引擎**：这是区别于市面 LMS 的核心。我们用**贝叶斯 Beta 分布 + 指数时间衰减**来建模每一项能力：

- 每项能力是一个 Beta(α, β) 分布，均值 α/(α+β) 映射到 level 1–5
- 每次事件归因产生 (Δlevel, confidence)，按共轭更新规则更新 α、β
- 单次事件最多让 α 或 β 增加 0.6（防止单一极端证据瞬间反转长期积累）
- 按能力类型应用差异化衰减速率（硬技能 λ=1/365、软技能 λ=1/1095、领域 λ=1/730）

**这背后的理论依据**：对应学习科学里的"遗忘曲线"（艾宾浩斯、Ebbinghaus）与"技能退化"（skill decay）研究——写代码半年不碰就生疏；沟通和问题拆解这类 metaskill 几乎不退化；业务知识介于两者之间。

**Phase 3 双视图交互**：引入"员工视角"和"L&D 全局视角"的切换，加上时间轴滑块——可以回溯任意一个时间点的员工能力画像和当时正在做的任务，看学习推荐是怎么随时间演化的。

### 7. 工作流：一次端到端调用是怎么走的？

```
员工选择目标岗位
    ↓
ExtractEmployee  → 员工能力画像
ExtractJob       → 岗位能力需求
    ↓
GapAnalyzer（结构化差值 + LLM 优先级裁判）
    ↓
七路 Recommender 并行召回（每路 Top-20）
    ↓
RerankResource 按 learning_mode 约束精排（每路 Top-5）
    ↓
GeneratePathway 合成 30 / 60 / 90 天路径
    ↓
展示给员工（四个 Tab 按 70-20-10 分组）
```

整条链路在 Mock 模式下端到端约 50 毫秒，真实 LLM 下约 2–3 秒。LLM 调用预算目标 ≤ 11 次/员工/次（七路精排如果合批成一次，可压到 ≤ 5 次）。

## 第二部分：Demo 讲解

Demo 有两个入口视角——**员工视角**和 **L&D 全局视角**——对应两类真实用户。

### 入口：AI 向导（Agent Wizard）

打开首页，第一步不是选菜单，而是**选身份**：

- 选"**我是员工**" → 下一步选自己是谁 → 选目标岗位 → AI 跑 6 步推理 → 看结果
- 选"**我是管理员 / L&D**" → 选关注的岗位或能力维度 → AI 跑 6 步组织体检 → 看结果

这里面有一个产品设计上的小讲究：**让"走流程"变成"对话式引导"**。传统 HR 系统让用户面对一堆菜单和下拉框，这里我们把流程压到 4 步，每步都是一个明确的选择，AI 在背后跑一个 6 阶段的推理计划（Plan）——员工能看到每一步在做什么、用了哪个 Skill、产生了什么中间结果。

**为什么这对 HR 汇报很重要**：因为 AI 的可解释性在 HR 场景是刚需。员工问"凭什么给我推这个课"，HR 同事必须能答得出来。所以我们把**证据溯源**贯穿到了每一张推荐卡片——`evidence` 字段记录"这个能力标签是从哪条简历、哪个项目、哪次 Code Review 推出来的"，一路可追溯。

### 页面 1：员工画像 / 组织能力分布

**员工视角**：
- 雷达图（硬 / 软 / 领域 / 工具四大类均值）
- 能力标签云（按 confidence 着色）
- 每条标签点开可以看证据溯源

**L&D 视角**：
- 同一个页面切换成"组织能力分布"
- 组织雷达（20 人平均）
- 能力覆盖度排行榜（L≥3 的员工数量）

**讲解重点**：同一套底层数据，两种视角。这是我们做数据产品的一个原则——**不要为不同用户建两套数据，而是让同一份数据有不同的切片方式**。HR 最头疼的"指标口径不一致"问题，根源往往就是两套表。

### 页面 2：岗位目标（JD Profile）

展示 JD 的**结构化能力清单**——每一项能力的 `need_level` 和 `weight`。JD 不再是一段自由文本，而是可以参与计算的对象。

**给 HR 的启发**：这个结构化 JD 可以反哺招聘——同样的结构可以直接用来做"候选人-岗位匹配"的自动初筛，比关键词搜索精细得多。

### 页面 3：差距分析（Gap Analysis）

核心产物：

- **雷达图叠加**：员工画像 vs 岗位需求，一眼看出缺在哪里
- **Gap 列表**：按 priority 排序，每条带 AI 生成的 rationale
- **Match Score**：0-1 之间的一个综合分，公式是 `Σ weight × min(have, need) / Σ weight × need`

**Match Score 的含义**：这是一个加权覆盖率——"这个岗位对我而言，我已经满足了多少？"。0.6 通常是一个"可以开始转岗"的分界线，0.8+ 意味着该考虑晋升而不是转岗。

### 页面 4：赋能推荐（七路并行 + 70-20-10 Tab）

这是整个 Demo 的高潮页。看点：

1. **四个 Tab**：🎯 在实践中学（70%）/ 👥 向他人学（20%）/ 📚 系统学习（10%）/ 🛠️ 工具直接用（正交）
2. **每张卡片**有 `learning_mode` 色带 + 来源徽章 + 推荐理由
3. **30 / 60 / 90 天路径图**：三阶段，每阶段明确"主 mode 组合"
   - 30d 打基础：formal + tool + social（低门槛入门）
   - 60d 在实践中学：experiential + social + formal（进入项目，有导师护航）
   - 90d 独当一面：experiential + social + tool（挑战产出，熟练工具）

**讲解重点**：**70-20-10 不是装饰，而是算法约束**。在 RerankResource Skill 的 Prompt 里，每种 learning_mode 都有独立的约束文案——例如 formal 会要求"路径清晰、2-4 周可完成、偏好微课+深度资料组合"，experiential 会要求"能动手产出可见成果、避免纯理论课程"。这让 AI 的推荐不是盲目堆资源，而是按学习科学的规律来组织。

### 页面 5：动态赋能双视图（Phase 3 核心）

这一页是我自己最喜欢的。屏幕左右两栏：

- **左栏**：某位员工 6 个月的行为流时间线（上千条事件按类型着色）
- **右栏**：对应时间点的能力画像雷达 + 当时正在处理的任务 + 系统为他推送过的学习卡片

顶部有一根**时间轴滑块**——你可以拖到 6 个月前，看这位员工当时是什么水平；拖到 3 个月前，看他经历了哪次 Code Review 之后某项能力的 level 从 2.8 跳到了 3.4。

**这里体现的是什么？** 是**学习行为的可归因性**。过去 HR 回答"某员工到底有没有成长"只能靠年底的主观评分，现在可以精确到"他的 Python 能力在第 45 天出现了显著跃升，对应事件是 PR #237——一次复杂的数据库迁移重构"。

### L&D 全局视角（管理员专用四页）

管理员身份走向导，会额外看到四个组织级分析页：

1. **🔥 组织能力热力图**（20 员工 × 36 能力的完整矩阵，按 level 着色）
2. **🌟 隐形专家图**（近 30 天某能力累积 Δ 最大的员工——他不一定是 Title 上的专家，但他最近在这个能力上产出最多）
3. **🎯 岗位匹配矩阵**（员工 × 岗位的 Match Score 网格，用来做内部转岗 / 继任者规划）
4. **📊 赋能 ROI 仪表**（某类资源被消费后对能力 level 的平均抬升幅度，回答"哪些课真的有用"）

**"隐形专家"这个设计值得单独说一下**——它回答了 HR 一个经典痛点：**"谁是组织里真正懂 X 的人"**。过去你要靠问，靠打听，靠 HR 自己记。现在通过观察行为流，系统自动识别出"近 30 天在能力 X 上产生最多证据"的人。这个人可能比 Title 上的"Tech Lead"更值得你去对接。

## 第三部分：边界与未来

做 Demo 的时候我一直在提醒自己——**不要吹牛**。所以我们在 v1.0 里**明确不做**这些事：

- **不覆盖**销售 / HR / 客服 / 法务 / 后勤等行为非数字化的岗位（数据基础不具备）
- **不做**团队 / 组织级赋能（没有 Team 数据模型）
- **不深入**软技能 / 心理维度（软技能归因 F1 上限太低，心理维度有伦理风险）
- **不替代**管理者判断（系统提供结构化证据，决策权永远留在人手里）

**列入 Phase 4 的四个扩展方向**：

1. **多岗位适配**：为销售、客服等岗位 ship 独立的"岗位包"（能力本体 patch + 行为流 schema + 资源池扩展）
2. **组织级赋能**：新增 Team / OrgUnit 数据模型，做配对推荐和团队能力热力图
3. **软技能精细化**：自评 + 360 反馈 + 情境模拟题三角验证，把软技能 F1 从 0.5 提到 0.7+
4. **生产化**：真实企业系统接入 + 合规护栏 + A/B 实验平台

## 第四部分：对 HR 研究与实践的启发

最后留 5 分钟做总结，我想提几个可以和同学们一起讨论的点：

### 1. 能力建模的范式在变

过去的胜任力模型是**静态词典**——编一本书，贴到墙上，几年更新一次。未来的胜任力模型是**活的分布**——每个人每项能力是一个贝叶斯分布，随着他每次产出、每次反馈持续更新。HR 研究里的"胜任力建模"方法论可以直接迁移，但要补一个维度：**时间**。

### 2. 70-20-10 从理念变成算法

70-20-10 法则在培训圈流传了 20 多年，但在大多数企业落到"70% 靠在岗"的时候就停了，因为没法运营。这个 Demo 告诉我们：**只要把"在岗实践机会"也数字化成可推荐的资源**（内部项目、Lab 环境、案例库），70-20-10 就从口号变成了可执行的算法约束。

### 3. 可解释性是 HR-AI 的红线

其他 AI 场景（广告、推荐电影）可以允许"黑箱准就行"。HR 场景不行——因为涉及人的职业发展和组织资源分配，每一个推荐都要能回答"为什么是他不是别人"、"为什么推这个不是那个"。这个 Demo 里大量精力花在**证据溯源**和**Skill 拆分**上，本质都是为了可解释。

### 4. 真正的难点不在 AI，在数据治理

讲了这么多，最想强调的一点是：**把这套系统在真实企业里跑起来，最难的不是调模型，而是把 6 类行为流接通、把能力本体和各业务系统的数据字典对齐、把合规护栏写到每一条数据链路上**。这些事情，恰恰是 HR 同学最该参与进来的——因为它关乎"员工会不会信任这个系统"，而信任一旦崩掉，再好的算法也白搭。

### 5. HR 研究可以做什么？

几个具体可以切入的研究问题：

- **70-20-10 的真实比例**：用行为流数据验证——在不同岗位、不同层级下，实际的能力成长到底有多少来自 experiential / social / formal？这是一个一直缺大样本数据的老问题，现在有可能回答。
- **衰减系数的实证标定**：λ 的经验值来自学习科学常识，但不同组织、不同能力类型的真实 λ 应该是多少？可以用面板数据估计。
- **Expert Finder 的效度**：算法识别的"隐形专家"和 360 评议的"同事公认专家"重合率有多高？如果不重合，是算法错了，还是组织的"公开知名度"和"实际产出"本来就脱节？
- **AI 推荐的公平性审计**：不同性别、不同司龄的员工，在同样能力水平下，收到的推荐分布是否一致？这是 HR-AI 伦理研究的关键议题。

## 收束

这个 Demo 目前的规模：代码约 4500 行，数据涵盖 36 项能力、20 名员工、10 份 JD、155 条资源、9400 条行为事件，可回溯 6 个月共 11788 条时间轴点。它是一个**能跑通完整闭环**的方法论验证，不是生产系统。

但它应该能说明两件事：

> **第一，"实时精准个性化赋能"不是科幻，是工程——把能力本体、行为流、赋能资源池、AI Skill 体系这四块拼起来就能做。**
>
> **第二，这件事落不落得下去，关键不在模型，在 HR 专业能不能深度参与到数据与流程设计里。**

技术可以外包，对"人"的理解不能。这是我做完这个 Demo 最想留给在座的一句话。
